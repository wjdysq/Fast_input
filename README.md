# 复制监听小程序
本程序绕过了复制粘贴的逻辑 使复制粘贴内容转化为手动快速输入 很好的应对了学*通等不允许复制的软件

监听剪贴板，把 Ctrl+C 复制的内容快速自动输入到指定窗口。

默认**逐字符快速键入**（形成连续输入效果），也可以切成瞬间粘贴。

零第三方依赖，只用 Python 标准库 + Win32 API。

---

## 快速上手

```bash
# 1. 自检，确认本机各环节正常
python selftest.py

# 2. 看看有哪些窗口可以当目标（记下标题）
python main.py --list-windows

# 3. 跑起来（默认：Ctrl+Alt+V，逐字键入到当前前台窗口，200 字符/秒）
python main.py

# 4. 调快/调慢逐字输入
python main.py --speed 300          # 300 字符/秒
python main.py --speed 50           # 慢到能看清每个字
python main.py --type-interval 0    # 不限速

# 5. 切成瞬间粘贴
python main.py --method paste

# 6. 更保守的用法：复制后延迟 2 秒自动输入，留时间切窗口
python main.py --mode delay --delay 2

# 7. 先试不真的输入，只看日志
python main.py --dry-run
```

## 核心功能

**`Ctrl+C` 复制 → 内容进缓存 → 按热键 → 逐字符快速键入到目标窗口。**

模块结构，各管一件事：

| 文件 | 职责 |
|------|------|
| `backend.py` | 平台抽象层 + 逐字键入引擎。Windows 用 ctypes 直调 Win32；macOS/Linux 是骨架 |
| `contents.py` | 内容归一化：多格式挑选、富文本降级、去重、防自触发 |
| `target.py` | 目标定位 + 输入。风险最高的部分，宁可放弃也不乱发按键 |
| `hotkey.py` | 全局热键（`GetAsyncKeyState` 轮询，不独占按键） |
| `ui.py` | 终端实时面板（纯 ANSI，零依赖）。状态 + 统计 + 滚动日志 + 进度条 |
| `config.py` | JSON 配置，所有行为可配 |
| `main.py` | 主循环 + 命令行 |
| `selftest.py` | 逐项自检，快速定位哪一环坏了 |

## 处理流程

```
剪贴板变化
  ├─ 原生事件 AddClipboardFormatListener（默认，几乎零开销）
  └─ 轮询（回退方案，间隔可配）
        ↓
  读剪贴板（text / html / rtf / image 都读）
        ↓
  格式归一化 → 挑一种表示 → 富文本降级为纯文本
        ↓
  去重（指纹 + 时间窗）→ 防自触发 → 空内容过滤
        ↓
  按触发模式决定何时粘：热键 / 立即 / 延迟
        ↓
  解析目标窗口 → 排除规则检查 → 抢焦点并二次确认
        ↓
  注入：Ctrl+V（快）或 KEYEVENTF_UNICODE 逐字输入（兼容性好）
        ↓
  换行/制表符单独走虚拟键码（VK_RETURN / VK_TAB），其余字符走 Unicode
```

## 目标位置的指定方式

三种模式，改 `target_mode`：

| 模式 | 含义 | 适用 |
|------|------|------|
| `foreground` | 粘到"粘的那一刻"的前台窗口 | 最灵活，手动切窗口后按热键 |
| `title` | 按标题子串匹配（不区分大小写），自动聚焦 | 固定往某个程序（如"记事本"）灌内容 |
| `handle` | 指定窗口句柄（用 `--list-windows` 查） | 精确控制，但句柄重启后会变 |

`title` 模式示例：

```bash
python main.py --target title --title "记事本"
```

> 注意：Windows 窗口标题里可能混入**零宽字符**（实测本机 Edge 标题里就有 `\u200b`），
> 所以匹配走"子串包含"而不是全等，更稳。

## 触发方式

| 模式 | 行为 | 建议 |
|------|------|------|
| `hotkey`（默认） | 复制后按 `Ctrl+Alt+V` 才粘 | 最可控，不会误触发 |
| `delay` | 复制后等 N 秒自动粘 | 留时间切窗口 |
| `auto` | 一检测到变化立刻粘 | 最快，但按键会落到你当时在的窗口 |

改热键：`python main.py --hotkey ctrl+shift+p`

## 配置

```bash
python main.py --init-config      # 生成 ~/.clip_autopaste.json
```

几个值得调的：

```json
{
  "trigger_mode": "hotkey",
  "hotkey": "ctrl+alt+v",
  "target_mode": "foreground",
  "paste_method": "type",
  "type_interval": 0.005,
  "type_show_progress": true,
  "poll_interval": 0.25,
  "dedupe_ttl": 2.0,
  "max_text_length": 0,
  "normalize_whitespace": false,
  "exclude_titles": ["密码", "Password"],
  "dry_run": false
}
```

- `paste_method`: `type` 逐字输入（默认），像人飞快打字；`paste` 发 Ctrl+V，瞬间完成但有些控件不响应
- `type_interval`: 秒/字符。`0.005` = 200 字符/秒；`0` = 不限速
- `exclude_titles`: **强烈建议留着**。命中这些标题的窗口一律不注入，防止粘进密码框
- `max_text_length`: 设个上限（如 5000）可防止误复制大段文本被灌进去

## 逐字快速键入是怎么实现的

目标：不要瞬间粘贴，而是像人在飞快打字一样，一个字符一个字符地打进去，
且**最终内容必须和原文逐字节一致**。

三个技术要点：

### 1. 用 `KEYEVENTF_UNICODE` 送字符码，而不是虚拟键码

每个字符编码成一对键盘事件（down + up），`wScan` 直接放字符码。
好处是绕过键盘布局与修饰键状态 —— 中文、emoji 都能原样输入，
且不会因为你正好按着 Shift 而变形。

### 2. BMP 外的字符必须拆成代理对（代理对是必须的）

`wScan` 是 `USHORT`，只有 16 位。而 emoji 这类字符码位超过 U+FFFF，
直接塞进去**高位会被截断**。

实测：`😀`（U+1F600）会被打成 `\uf600` —— 内容就错了。

正确做法是按 UTF-16 编码，BMP 外的字符自然拆成两个代理码元，分别发送：

```python
units = ch.encode("utf-16-le")          # BMP 外 -> 4 字节（2 个码元）
for i in range(0, len(units), 2):
    code = units[i] | (units[i + 1] << 8)   # 每个码元单独发一对事件
```

所以"每个字符 = 2 个事件"这个假设是错的，含 emoji 的文本按**码元**算：
`😀` 占 4 个事件，`中` 占 2 个。

### 3. 批量提交 + 精确计时

- **批量提交**：一次 `SendInput` 提交一批事件，而不是每字符调一次。
  系统调用开销摊薄掉，才谈得上"快"。
- **精确计时**：Windows 的 `time.sleep` 最小粒度约 15.6ms，
  想要 5ms 的间隔根本达不到（会被拖到 15ms+）。所以短间隔用
  `sleep` + 忙等待混合：先 sleep 掉大头，最后 1ms 忙等待微调。
  实测 20 次 5ms 等待，误差 0.1%。

速度换算：`type_interval = 0.005` → 200 字符/秒。

### 4. 输入前的内容校验（保证完整性）

输入前先离线跑一遍「编码 → 解码」往返，确认能无损还原：

```python
Injector._precheck(text)   # -> (是否通过, 原因)
```

不通过就**拒绝输入**，而不是打出一堆乱码。能拦住：
- 混进孤立代理项（lone surrogate）的非法文本
- 任何编码后与原文不一致的情况（会指出第几个字符出的问题）

### 5. `SendInput` 返回值必须检查

一次提交大量事件时，`SendInput` 可能只接受一部分就返回，
剩下的**静默丢弃** —— 这就是"最终内容不完整"的典型原因。

处理方式：没提交完就继续提交剩余部分；连续 3 次纹丝不动才判定被拒绝并报错。

### 6. 换行符必须走虚拟键码，不能走 Unicode

**这是"复制多行文本却挤成一行"的根因。**

`KEYEVENTF_UNICODE` 送的是字符码，系统把它当作"文本输入"处理 ——
送 `0x0D`（CR）或 `0x0A`（LF）进去，**不会产生换行效果**，只会被目标控件丢掉。

正确做法：换行走 `VK_RETURN`，制表符走 `VK_TAB`，只有普通字符才走 Unicode：

```python
def _char_events(ch):
    if ch == "\n":  return _vk_events(VK_RETURN)   # 0x0D
    if ch == "\t":  return _vk_events(VK_TAB)      # 0x09
    return _unicode_events(ch)                      # 其余走 Unicode
```

另外还有一个坑：`\r\n` 若原样处理会变成**两个回车 = 两个空行**。
所以输入前先把 CRLF/CR 统一成 LF：

```python
normalize_newlines(text)   # \r\n -> \n, \r -> \n
```

这样"Windows 风格"的多行文本也能正确还原成逐行排列。

### 7. 自适应降速（丢字的最后一层防护）

即使 `SendInput` 全部提交成功，目标应用也可能来不及处理而丢字。
`_send_input` 会记录本次是否发生过"部分接受"，逐字引擎据此动态调整间隔：

- 出现重试 → 间隔放大（最多 4 倍）
- 连续稳定 → 间隔逐步收回原值

这样慢的控件会自动放慢、快的控件保持满速，不需要你手动调。

## 终端实时面板

`ui.py` 提供一个纯 ANSI 的实时界面（零第三方依赖，Windows 上自动开 VT 模式）：

```
┌─ 剪贴板自动粘贴 ──────────────────────────────────── 监听中 ─┐
│ 状态     已捕获 1 条，等待热键 Ctrl+Alt+V                    │
│ 目标     前台窗口                                          │
│ 手法     逐字键入 200 字符/秒                              │
├─────────────────────────────────────────────────────────────┤
│ 已捕获 3   已输入 2   字符数 128   失败 0   均速 198 字符/秒 │
├─────────────────────────────────────────────────────────────┤
│ 18:12:03  已捕获 128 字符                                   │
│ 18:12:07  开始逐字键入 -> 记事本                            │
│ 18:12:08  [████████████████████] 100%  完成 128 字符 0.65s  │
└─────────────────────────────────────────────────────────────┘
```

- 宽度自适应终端（中文/全角按 2 列算），最窄 60 列
- 日志区自动滚动，保留最近 N 行
- 长文本输入时显示进度条
- 不支持 ANSI 的终端自动降级为带色纯文本输出
- 想要最朴素的输出：`python main.py --plain`


### 1. 剪贴板是共享资源，必须抢锁 + 校验

各种截图工具、剪贴板管理器、输入法都在监听剪贴板，会和你抢。实测本机上
**PixPin 常驻监听**，写入后可能立刻被它覆盖。

处理方式（`backend.py`）：
- `OpenClipboard` 失败会**重试**，不是一次失败就放弃
- 写入后**回读校验**，被覆盖了就整体重试（最多 3 轮）

### 2. `SendInput` 的结构体尺寸必须是 40 字节

这是最容易踩的坑。`INPUT` 是个 union，64 位下最大成员是 `MOUSEINPUT`（32 字节），
加 `type` 字段对齐后是 **40 字节**。用"占位 padding"近似 union 很容易算成 32，
而 `SendInput` 收到尺寸不符会**返回 0 静默什么都不做**。

代码里在模块加载时就 `assert sizeof(INPUT) == 40`，不匹配直接报错——
宁可启动失败，也不要静默失效。

同时 `SendInput` 的返回值**必须检查**，不能假设成功。

### 3. 抢焦点是最大的不确定性

`SendInput` 把按键发给"当前前台窗口"。如果目标没抢到焦点，内容就粘到别处了。

代码策略：
1. 注入前确认目标句柄
2. 不在前台就尝试聚焦，**等待并二次确认**（Windows 有前台锁限制）
3. 确认失败就**放弃本次粘贴**，而不是硬发按键

### 4. 中文/emoji 用 `KEYEVENTF_UNICODE`

逐字输入时用 Unicode 扫描码而不是虚拟键码，绕过键盘布局，
中文、emoji 都能原样输入。

### 5. 平台差异

| | 剪贴板事件 | 输入注入 | 备注 |
|---|---|---|---|
| Windows | `AddClipboardFormatListener` | `SendInput` | **完整实现** |
| macOS | 无公开通知，只能轮询 `changeCount` | `CGEventPost`，需辅助功能授权 | 骨架 |
| Linux X11 | XFixes 或轮询 | `xdotool` | 骨架 |
| Linux Wayland | 安全设计上禁止跨窗口读 | `ydotool`，需 uinput 权限 | 基本做不了 |

**Wayland 是硬限制**：设计上就不允许程序读别的窗口的剪贴板、也不允许向别的窗口发按键。

### 6. 注入可能被拒绝

以下情况合成输入会被目标忽略或拦截：
- 目标窗口**以管理员权限运行**，而本进程不是（UIPI 限制）
- 被安全软件 / EDR / 反作弊拦截
- 某些现代打包应用（Store 应用）的输入层不接收低完整性合成输入

这种情况 `SendInput` 可能返回成功但内容进不去——所以自检脚本第 9 项要真实验证。

## 限制

- **真实按键注入无法在受限会话（远程桌面、非交互式服务、某些沙箱）中验证**。
  我的测试环境正是这种情况：窗口能创建、能聚焦调用成功，但系统不让它成为前台，
  所以按键落到了别的窗口。代码逻辑已全部验证，注入需要你在普通桌面会话里跑
  `selftest.py` 第 9 项确认。
- macOS / Linux 后端只有骨架，能读剪贴板、能发粘贴键，但窗口定位未完整实现。
